## 新增：达梦连接诊断工具 demo/dmcheck

现场反馈「连达梦一直显示密码错误」，做了个独立诊断程序来定位根因。

### 交付物
- `demo/dmcheck/main.go`　单文件，**刻意不依赖 syncbase**（自带一份复刻 env.go 规则的极简解析），
  这样即使主程序被改坏，诊断工具照样能跑
- `demo/dmcheck/dmcheck.env`　配套配置模板，字段名与主程序 `.env` 完全一致，现场可直接比对
- `demo/dmcheck/README.md`　现场使用说明（已改名为 `dmcheck-使用说明.md` 放进交付目录）
- `demo/dist/dmcheck_linux_amd64`　7.7MB（比迁移程序小，因为不引 mongo-driver）
- 已同步到交付目录 `demo/迁移/`：`dmcheck`、`dmcheck.env`、`dmcheck-使用说明.md`，并刷新了迁移程序与 README

诊断分 6 步：配置文件定位 → 解析与字符体检 → DSN 构造对比 → DNS/TCP → 驱动与认证 → 库内连通性。
末尾有「诊断结论」区，每条 `finding` 都带「是什么问题 + 怎么办」。退出码 0=通 / 1=不通，方便脚本判断。

### 定位到的根因（已修复）
`syncbase/env.go` 的 `DMConfig.DSN()` 原本用 `url.URL` + `url.UserPassword` 构造连接串，
会把密码里的 `@ ? : # %` 空格等字符转义成 `%XX`。而达梦驱动的 `parseDSN`
（`gorm-dameng/dm8/n.go:714`）**只做字符串切分，不做 URL 解码**——按「最后一个 `@` 切账号、
第一个 `:` 切密码」取值。于是服务端收到的是 `P%40ss` 这种形态，
现象就是「账号密码明明正确，却一直报用户名或密码错误」。

已改为字面量拼接。密码不含需转义字符时两种构造方式产出的 DSN 完全相同，故对现有环境零影响。

**实测证据**（在 10.8.19.133:5236 建了临时账号 `DMCHK` / `P@ss#2024`）：

| 构造方式 | 驱动实际收到的密码 | 结果 |
| --- | --- | --- |
| url.URL + UserPassword | `P%40ss%232024`（13 字符） | ✗ `Error -2501: 用户名或密码错误` |
| 字面量拼接（修复后） | `P@ss#2024`（9 字符） | ✓ 认证成功 |

临时账号已 DROP，临时工具目录 `demo/_mkuser` 已删除，未留残留。
